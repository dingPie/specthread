## 1. 개요

이 프로젝트의 모든 문서가 따르는 형식 규칙. **도메인과 무관한 부분만** 담는다. 경로·마커 종류·상용구처럼 이 프로젝트에서만 성립하는 값은 [`project.md`](./project.md) 가 갖는다.

| 파일 | 담는 것 | 층 |
|-----|-------|---|
| `rules.md` | 형식 규칙, 참조 방식, 미확정 관리 | 코어 |
| [`project.md`](./project.md) | 이 프로젝트 고유 값 | 커스텀 |
| [`templates/spec.md`](./templates/spec.md) | 시스템 명세 템플릿 | 코어 |
| [`templates/plan.md`](./templates/plan.md) | 작업 계획 템플릿 | 코어 |

**어느 유형이 어느 템플릿을 쓰는지는 `config.docTypes` 가 정의한다.** 위 표는 파일 목록과 층 표시만 담는다.

### 2-1. 본문에 남기지 않는 시점·버전 정보

검사: `timestamp/body-date`

문서 본문은 **현재 상태와 그 근거만** 서술한다. 아래는 전부 하단 변경 이력으로 보낸다.

| 유형 | 예 |
|-----|---|
| 날짜 | `(2026-08-09 결정)` |
| 마일스톤·주차 라벨 | `(M1 신규)` / `(W6 추가)` |
| 시점을 함의하는 단어 | _신규_ / _도입_ / _추가_ / _신설_ |
| 구버전 대비 서술 | _"구 X 폐기"_ / _"기존 Y 흡수 후 삭제"_ / _"이전 안은 Z"_ |
| 결정 사건 라벨 | _"사용자 결정 (날짜)"_ / _"결정 #5"_ / _"N 차 라운드에서 확정"_ |

**미래 시점도 같다.** `계획 (M2-B)` 처럼 _언제 할 것인가_ 를 spec 본문에 적지 않는다. 해결 예정은 관리 문서의 항목이 소유하므로 (§4-2) 본문에도 적으면 두 곳을 고쳐야 하고 한쪽이 낡는다.

결정의 **내용** 과 **근거** 는 현재 상태이므로 본문에 남는다. 빼는 것은 _누가 언제 무엇을 뒤집었는가_ 라는 사건 기록이다. 코드 주석에도 같은 원칙이 걸린다.

### 2-2. 목차

검사:
- `toc/missing`
- `toc/stale`
- `heading/multiple-title`

제목 다음에 목록으로 둔다.

```markdown
**목차**

- [1. 개요](#1-개요)
- [2. 데이터 모델](#2-데이터-모델)
- [참조](#참조)
- [미확정 사항](#미확정-사항)
- [변경 이력](#변경-이력)
```

- 표시 문자열은 제목 원문 그대로. 앵커는 마침표를 지우지만 (`1. 개요` → `#1-개요`) 목차 이름은 손대지 않는다
- `##` 레벨만 넣는다. `###` 까지 넣으면 목차가 본문보다 길어진다
- 꼬리 절도 넣는다
- 기계가 채운다. 생성기가 `##` 목록에서 만들고 검사기가 일치를 확인한다
- `#` 제목이 둘 이상이면 생성기가 그 문서를 건너뛴다

### 2-3. 도식

**흐름·순서·상태 전이·의존 관계일 때만 mermaid 로 그린다.** 그 밖의 나열은 표나 목록으로 쓴다.

ASCII 박스 드로잉은 쓰지 않는다. 폭을 손으로 맞춰야 하고, 항목을 하나 추가하면 다시 그려야 하고, diff 가 읽히지 않는다.

### 2-4. 변경 이력 형식

검사: `changelog/order`

문서 맨 아래에 `| 날짜 | 내용 |` 표로 둔다.

| 규칙 | 내용 |
|-----|-----|
| 단위 | 한 커밋 = 한 줄. 같은 커밋 안에서 변경이 더 생기면 그 줄을 고쳐 쓴다 |
| 순서 | 오래된 순. 새 줄은 표 맨 아래에 붙인다 |
| 다시 쓰기 | 줄은 유지하고 내용은 다시 쓸 수 있다. 줄을 합치거나 지우지 않는다 |

정본은 git 이고 이 표는 요약본이다. 오래된 순인 이유는 최신 줄이 파일의 맨 끝에 놓여 가장 찾기 쉽고, diff 충돌 지점이 한 곳으로 고정되기 때문이다.

### 2-5. 꼬리 절 이름은 예약어다

검사:
- `heading/tail-name-reused`
- `heading/numbered-tail`

`참조` · `미확정 사항` · `변경 이력` 세 이름을 본문 절 제목으로 쓰지 않는다. 기계가 이름으로 꼬리 절 위치를 찾아 채우므로 (§3-3), 같은 이름의 본문 절이 있으면 엉뚱한 자리를 덮어쓸 수 있다.

같은 주제를 다루는 본문 절에는 한정어를 붙인다 - `참조 방식` / `참조 규칙` 처럼.

### 2-6. 문장 부호

검사:
- `style/em-dash`
- `style/rule-undeclared`

**em dash 를 쓰지 않는다.** 하이픈 `-` 으로 적는다.

강제: [`no-em-dash.mjs`](../tools/hooks/no-em-dash.mjs) 훅. `config.features.emDash` 가 `false` 면 비활성화.

## 3. 참조 방식

참조는 관계의 성격에 따라 둘로 갈린다.

| | 대상 | 관계 | SSoT |
|---|-----|-----|------|
| **단순 참조** | 문서 → 문서 | 가리키기만 한다 | 다른 문서 |
| **보완 참조** | 문서 ↔ 코드·데이터 | 서로 채워준다 | 문서가 의미를, 코드가 값을 |

지금은 대상 종류가 곧 판정 기준이 된다 (`.md` 냐 `.ts` / `.json` 이냐). 문서 ↔ 문서 보완 관계가 나오면 보완 참조 쪽을 넓힌다.

### 3-1. 단순 참조

검사:
- `link/target`
- `link/anchor`

내용을 가리키기만 하는 것. 본문 안 그 자리에 인라인 링크로 건다. 본문에 건 링크는 하단 참조 절에 기계적으로 모인다 (§3-3).

**내용을 옮겨 적을 때는 반드시 정본 링크와 범위 한정을 붙인다.**

```markdown
> **정본 2건**: auth.md / session.md
> 본 § 은 요약 + 인증 흐름 관련 부분만.
```

두 표기가 없으면 읽는 쪽이 이걸 정본으로 알고, 쓰는 쪽이 범위를 계속 넓힌다. 한 대상에 SSoT 는 하나다.

### 3-2. 보완 참조

**코드·데이터가 값을 갖고, 문서가 의미를 갖는 것.** 서로가 서로를 필요로 한다.

| 종류 | 값의 정본 | 문서가 갖는 것 |
|-----|---------|------------|
| enum / 상수 | 코드 | 각 값의 의미 |
| 설정 / 데이터 | 데이터 파일 | 왜 이 구성인가, 역할 분담 |
| 조감 | 코드 (여러 파일에 흩어짐) | 한 장으로 모은 흐름 |
| 수치 / 제약 | **문서** | 검증 대상 값 자체 |

- 설정/데이터 종류는 항목의 내용을 전재하지 않는다. 이름·타입·역할 한 줄까지. 그 이상은 링크로
- 아직 데이터가 없는 항목도 본문에 둔다. 구현 여부는 링크 유무로 드러낸다
- 아직 정하지 않은 것은 미확정 사항 절로 간다
- 수치/제약은 문서가 정본이다. 판정 기준: _이 문서대로 코드가 짜였는지 검증할 수 있는가_
- 역방향 링크가 건강 지표다. 코드가 해당 절을 가리키지 않으면 검사기가 경고한다
- 한 대상에 소유 절은 하나다. 겹치는 쪽에 소유처를 한 줄 적는다

### 3-3. 참조 절 - 기계 생성

검사:
- `reference/missing`
- `reference/stale`

문서 하단에 두고 본문 링크를 모아 자동으로 채운다. 사람이 쓰지 않는다.

```markdown
## 참조

### 문서
- [`auth.md`](./auth.md) - §1, §4

### 코드·데이터
- [`auth.config.ts`](../../src/config/auth.config.ts) - §3-1
```

같은 대상을 여러 번 가리키면 한 줄로 합치고 어느 절에서 참조됐는지를 붙인다.

**자동 로드되는 룰 문서는 참조 절을 두지 않는다.** 매 세션 통째로 읽히는 문서는 모든 줄의 비용을 반복해서 내고, 이미 사람이 큐레이션한 라우팅 표를 갖고 있다. 대상은 [`project.md`](./project.md) 가 지정한다.

### 3-4. 참조와 절 폐기

본문 절이 **링크만 담고 자체 설명이 없으면** 그 절은 존재 가치가 없다. 해당 내용을 인라인 참조로 대체하고 절을 지운다. 이것이 _절 폐기 판정_ 이다.

| 위치 | 규칙 |
|-----|-----|
| 인라인 링크 | 자유. 개수·위치·반복 제한 없음 |
| 본문 절 | 링크만 담은 절은 두지 않는다 (폐기 대상) |
| 하단 참조 절 | 유일한 예외. 링크만 담고 기계가 채운다 |

인라인이든 절이든 내용을 옮겨 적었으면 정본 링크와 범위 한정을 붙인다 (§3-1). 판정 기준: **여기서 그 개념을 직접 설명했는가.**

```markdown
설명 안 함 (자유)
  인증 흐름은 [`auth.md`](./auth.md) 참조

설명함 (정본 링크 필수)
  결제 취소는 상태 머신 전이로 처리된다.
  (정본 [`payment.md`](./payment.md) §3 - 본 절은 취소 흐름만)
```

검사기가 참조를 수집할 때 이 판정이 부산물로 나온다.

| 검사기가 보는 것 | 판정 |
|--------------|-----|
| 코드를 가리키고 코드도 이 절을 가리킴 | 보완 참조. 정상 |
| 코드를 가리키는데 코드는 안 가리킴 | 보완 참조. 역방향 링크 누락 |
| 문서만 가리킴 + 자체 설명 있음 | 단순 참조. 정본 링크 표기 검사 |
| 문서만 가리킴 + 자체 설명 없음 | 절 폐기 대상 |

판정은 절 단위다. 한 문서 안에 두 종류가 섞일 수 있다.

### 3-5. 절을 가리키는 표기

검사:
- `section-ref/missing`
- `section-ref/not-linked`
- `section-ref/unknown-doc`
- `section-ref/ambiguous-doc`
- `section-ref/no-doc-name`

다른 문서의 절을 가리킬 때는 앵커 링크를 쓴다.

```markdown
[`auth.md` §3](./auth.md#3-인증-흐름)
```

| 자리 | 표기 | 이유 |
|-----|-----|-----|
| 문서 → 다른 문서 | 앵커 링크 | 링크를 걸 수 있다 |
| 문서 → 자기 절 | `§N` | 가릴 문서명이 없다 |
| 코드 주석 | `파일명 §N` | 주석에는 마크다운 링크가 없다 |

`§` 는 링크를 걸 수 없는 곳에서만 쓴다. 링크로 대체할 수 있는 자리에서는 앵커 링크를 우선한다. 어느 쪽이든 번호가 밀리면 깨지지만, 검사기가 잡으므로 조용히 어긋나지 않는다.

## 4. 미확정 관리

미확정은 세 곳에서 같은 slug ID 로 관리된다. 정본은 관리 문서 하나이고 나머지 둘은 생성된 뷰다.

용어를 셋으로 고정한다.

- **미확정**: 아직 결정되지 않은 것 (개념어)
- **관리 문서**: 미확정 항목을 모아 두는 파일 (`pending.md`)
- **미확정 사항**: 각 문서 하단에 생성되는 `## 미확정 사항` 섹션

| 위치 | 역할 | 담는 것 |
|-----|-----|-------|
| 본문·코드 마커 | 발생 지점 표시 | slug + 힌트 한 줄까지 |
| 문서 미확정 사항 절 | 생성 뷰 | 관리 문서에서 가져옴 |
| 관리 문서 | **정본** | 상세 설명 + 백링크 |

설명은 관리 문서에만 상세히 쓴다. 마커 옆에 긴 설명을 두면 관리 문서와 어긋난다.

`PENDING` 접두는 마커에만 붙는다. ID 자체는 세 위치가 같다.

| 위치 | 표기 | 모양 |
|-----|-----|-----|
<!-- @specthread-ignore -->
| 마커 | `PENDING::deps::auth-flow` | 산문·주석 안 |
| 관리 문서 항목 | `` `[deps::auth-flow]` `` | `###` 헤딩 |
| 문서 미확정 사항 절 | `` `[deps::auth-flow]` `` | `li` |

마커는 산문 안에 박히므로 자기를 식별할 `PENDING` 접두가 필요하다. 관리 문서와 미확정 사항 절은 위치 자체가 맥락이므로 접두 없이 id 만 쓴다. `grep -c "PENDING::design"` 이 실제 발생 지점만 세는 것도 이 구분 덕분이다.

미확정 사항 절은 관리 문서의 백링크를 뒤집어 자동 생성한다 (검사: `pending/section-stale`). 절이 이미 있는 문서만 채운다.

### 4-1. 마커

형식은 세 조각 고정이다.

```
PENDING::<종류>::<slug>
```

| 요소 | 규칙 |
|-----|-----|
| `PENDING` | 고정 접두 |
| 종류 | 소문자. `system` 은 코어 예약, 프로젝트 종류는 `config.markers.types` 에서 정의 |
| slug | 전역 유일, kebab-case |
| 구분자 | `::` 통일 |
| 표기 | 문서에서는 백틱으로 감싼다 |

**종류**는 미확정의 성격을 나타내며, 사실상 _누가 처리하는가_ 를 가른다. `system` 은 코어가 소유하는 예약 종류로, 문서 체계 자체에 대한 미확정에 붙인다. 코어 문서가 커스텀층 종류에 의존하면 다른 프로젝트에서 깨지므로 이 분리가 필요하다. 종류가 여러 성격에 걸칠 때는 **대상 도메인이 우선**한다. 차단 원인("다른 작업이 끝나야 한다" 등)은 종류가 아니라 관리 문서 항목 본문에 적는다.

**slug**는 관리 문서 항목과 1:1 또는 N:1 로 대응한다. 여러 곳에 흩어진 잠정 값에 같은 slug 를 붙이면 관리 문서 항목 하나에 백링크 여러 개로 잡힌다. 필요한 만큼 세분하거나 넓게 묶는다.

마커에 넣지 않는 것:

- **해결 예정**: 마일스톤은 자주 밀린다. 관리 문서 항목이 소유한다
- **시점**: slug 에 `api-version-M2` 처럼 넣으면 시점이 바뀔 때 ID 가 바뀌고 모든 참조가 깨진다

```
코드    // PENDING::deps::auth-flow
문서    `PENDING::design::cache-strategy`
JSON    "_pending": "style::api-version"
```

힌트가 필요하면 마커 뒤에 ` - ` 로 한 줄까지 이어 붙인다.

검사기가 양방향으로 확인한다.

- `marker/orphan`: 코드 마커 ID 가 관리 문서에 없음 (추적되지 않는 미확정)
- `marker/unmarked`: 관리 문서 항목 ID 가 코드나 문서에 없음 (이미 해결된 것)

### 4-2. 관리 문서

검사:
- `pending/item-shape`
- `pending/inline-body`
- `pending/inline-options`
- `pending/work-link`
- `pending/timepoint`
- `pending/summary-missing`
- `pending/summary-stale`

미확정 항목을 `pending.md` 한 파일에 모으고 id 순으로 정렬한다.

관리 문서 안에서 종류마다 `##` 섹션을 하나씩 둔다. 종류 값은 `config.markers.types` 가 정의한다.

```markdown
## 2. design
## 3. system
```

**항목 형식**

```markdown
### `[deps::auth-flow]` 인증 흐름 결정

작성일 2026-05-02 / 해결 예정 M2

현재 세션 기반이나 토큰 기반으로 전환이 논의 중이다.

- (a) JWT 기반 토큰으로 전환한다
- (b) 현행 세션 유지

참조: [`auth.md` §2](../spec/auth.md), [`api.md` §4](../spec/api.md)
```

| 조각 | 규칙 |
|-----|-----|
| 헤딩 | `###` + id + 제목. 본문을 이어 붙이지 않는다 |
| 시점 | 헤딩 다음 줄. `작성일 <날짜> / 해결 예정 <라벨>` |
| 본문 | 문단 단위 |
| 선택지 | `li` 로 낸다 |
| 참조 | 마지막 줄 |

- 항목이 `###` 헤딩인 이유: `li` 는 앵커가 없어서 다른 문서가 개별 항목을 가리킬 수 없다
- 시점을 헤딩에 넣지 않는 이유: 마일스톤이 밀리면 앵커가 바뀌고 링크가 깨진다
- 번호를 붙이지 않는 이유: 항목을 끼우면 뒤가 전부 밀린다. 항목은 id 로 가리킨다
- 본문에 굵기(`**`)를 쓰지 않는다. 정보를 굵기로 나르면 무엇이 중요한지 흐려진다
- 체크박스를 두지 않는다. 해결되면 항목을 지우므로 `[x]` 상태가 존재하지 않는다

**시점 표기**

`작성일`(항상 과거)과 `해결 예정`(항상 미래) 두 라벨로 구분한다. 해결 예정이 없으면 생략한다.

- 해결 예정에 달력 날짜를 쓰지 않는다. 작성일과 같은 모양이 되면 구분이 안 된다
- 라벨 값은 검사하지 않는다. 새 프로젝트는 마일스톤 목록이 비어 있으므로, 집합 검사를 걸면 첫 항목부터 위반이 된다. `config.markers.timepoints` 는 참고 목록이지 검사 관문이 아니다

**등록 기준**

_정하지 않으면 무엇이 막히는지_ 말할 수 있어야 한다. 이것이 미확정과 할 일을 가르는 기준이다. 아무것도 막지 않으면 담지 않는다. 이미 결정된 것은 해당 도메인 spec 이 갖는다.

- 슬러그만 두지 않는다. 무엇을 정해야 하는지 알 수 있어야 한다
- `docs/work/` 문서를 가리키지 않는다. 작업 문서는 흡수 후 사라지므로 근거를 항목 안으로 옮긴다
- 해결되면 항목을 지운다. 단순 해소는 변경 이력에도 적지 않는다 (`git log -p` 가 기록을 갖는다). slug 가 다른 항목으로 흡수된 경우만 이력에 메모한다

**자동 생성**

- 백링크: slug 로 `grep` 해서 코드·문서 위치를 자동 수집한다
- 요약 표: 각 절 머리에 `| id | 항목 | 해결 예정 | 걸린 곳 |` 표를 자동 생성한다. 세 열 모두 손으로 셀 수 없는 값이라 `stale` 검사로 어긋남을 잡는다
- 마커가 없는 미확정(문서 전체에 걸리는 것)도 담는다. 백링크에 해당 문서만 적는다

## 5. 규칙 변경 절차

문서를 고치다 보면 규칙이 안 맞는 곳이 나온다. 그때 바로 규칙을 바꾸지 않는다.

| 단계 | 처리 |
|-----|-----|
| 1 회차 발견 | 그 문서에서만 예외로 처리하고, 이 파일 미확정 사항에 ID 를 붙여 기록한다 |
| **2 회차 발견** | 규칙을 고친다. 한 번은 우연, 두 번은 패턴 |
| 규칙 변경 시 | 기록해둔 항목을 지우고 변경 이력에 한 줄 |

기존 문서의 소급 적용:

| 변경 종류 | 소급 | 이유 |
|---------|-----|-----|
| **형식** (표기·순서·이름) | 한다 | 기계 치환이 되는 것만 |
| **구조** (절 추가·삭제·분할) | 안 한다 | 다음에 그 문서를 손댈 때 함께 |
